# Data model and policies

All records use UUID primary keys generated by PostgreSQL and timezone-aware timestamps.

## Tables

| Table | Purpose |
| --- | --- |
| `brands` | The organisation whose content is reviewed. Name is unique, case-insensitive. |
| `source_documents` | Uploaded PDF, text or CSV. Metadata, processing status, content hash, extracted text. File bytes live on disk, never in the database. |
| `document_sections` | Locatable extracted text: one row per PDF page, text block (with line range) or batch of CSV rows (with headers and row numbers in `meta`). |
| `approved_facts` | The Claim Ledger foundation: name, value, qualifications, unit, category, approval status, validity dates, owner, source reference. |
| `fact_revisions` | Append-only history written in the same transaction as every create, edit and status change. |

## Extracted versus approved

The four stages are separate in the schema and the interface.

1. Uploaded source: a `source_documents` row.
2. Extracted information: `document_sections` text. Nothing in it is a fact.
3. Proposed fact: an `approved_facts` row with `status = proposed`. This is the default for every new fact.
4. Approved fact: `status = active`, set only by an explicit action (the approve button, the status endpoint, or creating with `status: active`). It records `approved_by` and `approved_at`.

## Approval status versus validity

`status` is the approval lifecycle: `proposed`, `active`, `rejected`, `expired`, `retired`.
Validity comes from `valid_from` and `expires_at` (inclusive last valid day).
The API combines both into `effective_state`, evaluated against today's date on every read:

| effective_state | Meaning |
| --- | --- |
| `current` | Approved, started, not past its expiry date |
| `pending` | Approved but `valid_from` is in the future |
| `expired` | Marked expired, or approved but past `expires_at` |
| `unapproved` | `proposed` or `rejected` |
| `retired` | Withdrawn |

A fact with no `expires_at` is never reported as valid forever: it carries the `no_expiry_date` warning.
`review_state` (`overdue`, `due_soon`, `scheduled`, `unscheduled`, `not_applicable`) comes from `review_date` and `REVIEW_WARNING_DAYS`.

## Status transitions

proposed to active or rejected; active to proposed, expired or retired; rejected to proposed; expired to active or retired; retired is final.
A reason is required for rejected, expired and retired. Approving a fact whose expiry date has passed is refused.

## Editing approved facts

Changing name, value, category, qualifications, unit or the source of an `active` fact returns it to `proposed`, so changed wording is approved again.
Changing owner or the date fields keeps it active. Every edit stores old and new values in `fact_revisions.changes` and a full snapshot.
Edits accept `expected_version`; a stale value returns 409 `version_conflict`.

## Provenance policy

Every fact must either cite a document or state a manual source.
* Document source: `source_document_id` (must exist, belong to the same brand, be processed and not archived), optional `source_page` (PDFs only, within the page count) and `source_excerpt`.
  The excerpt is checked against the extracted text of that page (or whole document) and `source_excerpt_verified` records the result. An unverified excerpt is saved but flagged.
* Manual source: no document, and `source_note` is required (who confirmed it and how).
Both rules are also database check constraints. The same-brand rule is a composite foreign key `(source_document_id, brand_id)` to `source_documents(id, brand_id)`.

## Document policies

* Upload limit: `MAX_UPLOAD_BYTES` (default 10 MB), enforced while streaming. Oversize: 413, nothing stored.
* Type detection checks content, not only the filename: `.pdf` must start with `%PDF-`; `.txt` and `.csv` must be UTF-8 with no binary content. Mismatch or unsupported type: 415, nothing stored, no record.
* Duplicates: identical content (SHA-256) in the same brand is refused with 409 while a live copy exists. A failed or archived copy does not block re-upload. Enforced by a partial unique index.
* Corrupt or unreadable file of a valid type (corrupt PDF, scanned PDF without text, CSV without data rows, password-protected PDF): the record is kept with `processing_status = failed` and a readable `error_message`; the stored file is removed and the record cannot be cited by facts.
* Delete: refused with 409 `document_in_use` while any fact cites the document. Archive instead. An archived document stays attached to the facts that cite them (flagged `source_document_archived`), is hidden from the default list, and cannot be cited by new facts. Unrelated edits to such a fact still work.
* Storage: files are written under `STORAGE_DIR/<brand_id>/<document_id>.<ext>`. The client filename is never used in a path and is only a sanitised display name. Absolute paths are never returned. Downloads are served as attachments with `nosniff` and a sandboxing content-security-policy; only PDFs can be shown inline.

## Prepared for later phases

* Phase 2 (ProofGraph) can reference `document_sections.id`, `source_page` and `source_excerpt` as evidence.
* Phase 3 (fact-change propagation) can use `fact_revisions` and `approved_facts.version` to detect what changed, and `source_document_id` to find facts affected by a document.
* Brands are first-class, so content, findings and decisions can later hang off `brand_id`.

## Phase 2: content, reviews, claims, findings

| Term | Table | What it is |
| --- | --- | --- |
| Submitted content | `content_submissions` | The text a creator submitted. Saved exactly as submitted and not editable in Phase 2, so offsets stay valid. A later phase adds versions. |
| Review run | `review_runs` | One analysis of one submission. Re-reviewing adds a run; nothing is overwritten. Holds status, analysis mode, provider and model, error code, the content hash reviewed, and a summary (limitations, notes). |
| Claim | (columns on `review_findings`) | A span of the submission, `start_offset` to `end_offset`, that the engine decided needs verification, with a category and how it was found. `(review_run_id, claim_index)` identifies it within a run. |
| Review finding | `review_findings` | The verdict on one claim in one run: status, severity, explanation, recommended action, human-review flag, method, and `matched_fact_id`. |
| Finding evidence | `finding_evidence` | A link from a finding to a real approved fact and/or document section, with a snapshot of the fact and passage as shown at review time. |

A claim is not its own table in Phase 2 because it has no life outside a run. Phase 3 finds affected content through `finding_evidence.fact_id` and `fact_version`, and `review_findings.matched_fact_id`, both indexed.

### Integrity (enforced by the database)

* Composite foreign keys that include `brand_id` keep a run inside its content's brand, a finding inside its run's brand, and evidence inside its finding's brand and its fact's, document's and section's brand. `approved_facts (id, brand_id)` and `document_sections (id, document_id)` gained unique constraints in migration 0002 to allow this. No Phase 1 data or column changed.
* Evidence must reference an approved fact or a document section, and every role except `related_source` requires a fact.
* Facts and documents that evidence cites cannot be deleted (`RESTRICT`).
* Check constraints: finding `status` (five values), `severity`, `claim_category`, valid offsets, run `status` and `analysis_mode`; a finished run has `completed_at`; a failed run has `error_code`; `completed` implies full mode and `completed_limited` implies limited mode.

### Finding statuses

| Status | Rule |
| --- | --- |
| `supported` | A **current** approved fact states the same value in comparable units, and the claim states the fact's conditions. |
| `conflicting` | A current approved fact has a different value, or the claim is broader than the fact ("always 18 hours" against "up to 18 hours"), or the claim uses an avoided term or a misspelled approved name. |
| `outdated` | The claim matches a fact whose effective state is `expired` or `retired`, and no current fact supports it. |
| `uncertain` | Evidence exists but cannot be resolved: conditions omitted, wording narrower or broader than approved, units not comparable, different conditions, current facts that disagree, a possible paraphrase, or the model could not decide. |
| `unsupported` | No current approved evidence was found. Facts that are proposed, rejected or not yet valid are named in the explanation but never used as evidence. |

Only the effective state `current` (approved and inside its validity dates) counts as evidence. Another brand's facts are never retrieved.

### Model output

Model responses are parsed into fixed Pydantic shapes. Invalid output fails the run. Claim text that is not found verbatim in the draft is dropped. Fact ids that were not retrieved for that claim are dropped (the run notes the count). A model "supports" never overrides a deterministic numeric conflict, and AI-assisted findings always require human review.


## Phase 3: fact-change impacts (Claim Ledger)

| Term | Table | What it is |
| --- | --- | --- |
| Impact | `fact_change_impacts` | One content submission that needs another review because of **one** fact-change event. Created by BrandPR, never edited by it afterwards. |
| Affected finding | `fact_change_impact_findings` | Links an impact to the historical findings (and the evidence row, when there is one) that made the content depend on the fact, with the fact version each one relied on. |

An impact points at existing records and never changes them. `review_findings`, `finding_evidence`, `review_runs` and `content_submissions` are not written to by propagation (a test compares full row snapshots before and after). A historical review stays an accurate record of what was approved when it ran; the impact is the separate statement that it may be out of date.

### Events

| `trigger_type` | `trigger_key` | When |
| --- | --- | --- |
| `fact_revision` | `revision:<fact_revisions.id>` | `update_fact` or `change_status` saved a revision that invalidated approved evidence. `fact_revision_id` is set. |
| `fact_expiry` | `expiry:<fact_id>:<expires_at>` | A fact stored as `active` has an `expires_at` earlier than today (the date is inclusive, as in `effective_state`). `fact_revision_id` is null: expiry needs no edit. |

The expiry key deliberately omits the fact version: an owner-only edit after the lapse bumps the version without changing the expiry event, and must not create a second impact.

### Which changes are material

The change is judged by comparing the **revision snapshot before** with the one **after** (not the current fact), and only if the fact was `current` before the change. Otherwise nothing approved was relied on at that moment.

| Change | Result | `change_type` |
| --- | --- | --- |
| `name`, `value`, `category`, `unit`, `qualifications`, `source_document_id`, `source_page`, `source_excerpt`, `source_note` | Impact | `material_edit` |
| Status leaves approved (to `proposed`, `expired`, `retired`) with no content field changed | Impact | `no_longer_approved` |
| `valid_from` / `expires_at` edited so the fact is expired or not yet valid today | Impact | `validity_changed` |
| `valid_from` / `expires_at` edited and the fact is still current (for example extended) | None. The fact is assessed and stays valid; a later lapse is caught by the expiry sweep. | |
| `owner`, `review_date` | None (administrative; the reminder date does not invalidate an approval in Phase 1) | |
| Approval of a proposed fact, any edit to a fact that was not current | None | |

### What counts as reliance

A content submission is affected when a **completed** (`completed` or `completed_limited`) review run contains a finding that

* has a `finding_evidence` row for the fact whose saved `fact_effective_state` was `current` and whose saved `fact_version` is older than the version created by the event (**basis `evidence`**), or
* names the fact in `matched_fact_id` but has no evidence row for it (for example an undecided match). The version is then inferred from the revision timeline: the last revision saved at or before the run started, and only if it was approved and valid on that day (**basis `matched_fact`**).

Failed, pending and running runs never count. Evidence saved when the fact was already expired is not reliance on a current approval (that review already reported the fact as outdated). The queries are filtered by `brand_id` and the foreign keys are composite, so another brand's content is never matched.

### Previous and current versions

`previous_fact_version` is the version the affected review relied on (from the evidence snapshot, or inferred for `matched_fact`). `current_fact_version` is the version created by the change (for expiry: the fact's version when the lapse was detected). The historical wording is `change_summary.previous_snapshot`, copied from the `fact_revisions.snapshot` of `previous_fact_version`; the new wording is `change_summary.new_snapshot`; the live fact is read at request time. The three are shown separately and never merged. When several runs of one content item relied on the fact, the impact names the most recent run in `source_review_run_id` and links the findings of all of them.

### Duplicate prevention (enforced by PostgreSQL)

* `UNIQUE (trigger_key, content_submission_id)`: one impact per content item per event. Inserts use `ON CONFLICT DO NOTHING`, so two concurrent requests cannot both create it (tested with two threads that have both computed the same candidates before either writes).
* `UNIQUE (finding_id, fact_id)` on the link table: a historical finding is attributed to the first event that invalidated the fact it relied on. A later change to the same fact does not re-flag it; only findings from reviews made after the fact was approved again are flagged by the later event.
* Several findings or evidence rows of one content item for one fact give one impact with several links.

### Integrity

* Composite foreign keys keep an impact inside one brand: `(fact_id, brand_id)`, `(content_submission_id, brand_id)`, `(source_review_run_id, brand_id)`; links also reference `(finding_id, brand_id)` and `(review_run_id, brand_id)`. `(fact_revision_id, fact_id)` references `fact_revisions (id, fact_id)` so a revision must belong to the same fact. Migration 0003 adds `uq_fact_revisions_id_fact_id` as that key target; no Phase 1 or 2 column changed.
* All references are `RESTRICT`: a fact, content item, run or finding that an impact points at cannot be deleted. Only the link rows cascade from their impact.
* Checks: `trigger_type`, `change_type`, `status`; a revision trigger has a revision id and an expiry trigger does not; `previous_fact_version >= 1` and `current_fact_version >= previous_fact_version`; a link has an evidence id exactly when its basis is `evidence`.
* Indexes: `(brand_id, status)`, `(brand_id, created_at)`, `fact_id`, `content_submission_id`, `fact_revision_id`; links by `impact_id` and `fact_id`.
* `status` is `needs_review` when Phase 3 creates an impact. Phase 4 widened the check to `resolved` and `dismissed` (see below); Phase 3 itself never closes anything.

### Transactions

For revisions, `update_fact` and `change_status` call propagation after writing the revision and **before** their single commit. The fact change, its revision and its impacts are saved together or not at all; if recording impacts fails, the edit is rolled back and the caller receives an error (tested with a database error raised mid-propagation: the fact, version and revisions are unchanged). Nothing is queued: there is no outbox to drain. `propagate_revision_by_id` can re-run a stored revision safely.

If a fact had already lapsed by date when it is edited, that lapse is recorded as an expiry impact first (otherwise moving the fact to `proposed`, or extending its date, would hide the lapse from the sweep). The revision then sees a fact that was not current and adds nothing.

### Expiry detection

Expiry has no row to hook into, so `detect_expired(brand)` runs on demand at the start of every impact list, fact-impact list and summary request. It is **not** a background job: an expiry is recorded the first time someone asks after the date passes. It selects the brand's `active` facts with `expires_at < today` that have any review history, takes a per-brand advisory lock so concurrent requests serialise, skips facts that are being edited at that moment (that edit records the lapse itself), and inserts idempotently. A failure fails the request; an unreadable ledger is never shown as an empty one. `today` comes from `app.core.clock.today()`, which tests patch and which `CLOCK_OFFSET_DAYS` can shift in non-production environments.

### Source archival

Archiving a document sets `archived_at` and keeps the facts that cite it valid, with a `source_document_archived` warning (Phase 1 policy, unchanged). It does not make fact evidence unavailable to new reviews, so it creates no impact. Impact details show whether the cited source is now archived. Changing which document a fact cites is a source change and is material.

## Phase 4: revisions, approval workflow, impact resolution

Migration `0004` is additive. It backfills every existing submission as **revision 1 of its own new asset** (nothing is moved or rewritten, reviews and impacts keep their references).

### Content assets and immutable revisions

```
content_assets (id, brand_id, title, created_by, created_at, updated_at)
      1 --- n
content_submissions  = one immutable REVISION
      + asset_id, revision_number, parent_submission_id, workflow_status, change_note
```

* A revision's `content`, `content_hash`, `title`, `submitted_by`, `asset_id`, `revision_number`, `parent_submission_id` and `change_note` can never change: a database trigger (`brandpr_guard_revision`) rejects the UPDATE. Only `workflow_status` moves, and only along `draft -> in_review -> approved | changes_requested | rejected`; the trigger enforces that too.
* `UNIQUE (asset_id, revision_number)` and `UNIQUE (parent_submission_id)` give a linear history and are the backstop against two simultaneous revisions with the same number. `create_revision` also locks the asset row, so the loser gets `409 revision_conflict`.
* Composite foreign keys `(asset_id, brand_id)` and `(parent_submission_id, asset_id)` make a cross-brand asset or a parent from another asset impossible. `parent_submission_id IS NULL` exactly when `revision_number = 1`.
* `CHECK content_hash = sha256(content)` is enforced in the database.
* Review runs, findings and evidence still reference the submission (revision) they were created for. Nothing is retargeted to a newer revision.

### Workflow history (append-only tables)

Triggers reject UPDATE and DELETE on all four tables below.

| Table | Meaning |
|---|---|
| `workflow_events` | One row per step of one revision: `created`, `submitted`, `approved`, `changes_requested`, `rejected`, with actor, role, rationale, the review run and (for change requests) linked `finding_ids`. A partial unique index allows at most one final decision per revision. Decisions must be by a `reviewer`; changes and rejections need a non-blank reason. |
| `risk_overrides` | A reviewer's reasoned acceptance of one high-risk finding, recorded with the approval. The finding must belong to the named review run (composite FK). The finding row is never changed. |
| `revision_corrections` | What the creator did with a finding when writing a revision: `accepted` / `rejected` / `modified` a suggestion, or corrected `manual`ly, with the original and replacement text. Suggestions themselves are not stored. |
| `fact_change_impact_resolutions` | How a Phase 3 impact was closed (see below). |

### Impact resolution

`fact_change_impacts` keeps its Phase 3 meaning. Phase 4 adds the statuses `resolved` and `dismissed`:

* A trigger (`brandpr_guard_impact`) forbids changing any triggering column (fact, revision, versions, reason, summary, `created_at`...). The **status** may change only from `needs_review` to the value recorded in a `fact_change_impact_resolutions` row for that impact. No re-open, and no status change without a resolution row.
* `fact_change_impact_resolutions` is the historical decision: `action` (`resolved`/`dismissed`), previous and resulting status, actor (always a reviewer), rationale, and for `resolved` the resolving revision, the approving review run and the approving workflow event (all required by a CHECK). `UNIQUE (impact_id)`: an impact is closed once.
* The impact's own `content_submission_id` still names the revision that was originally reviewed. The resolving revision, review run and decision are separate references.

A resolution is only accepted when (checked in `services/impact_resolution.py`): the resolving revision is newer than the affected one, same asset and brand, and `approved`; its approval names a finished review run of exactly that revision whose hash matches the stored text; that run started after the impact was recorded; the fact was not revised again after it; evidence about the fact in that run is for the fact's current version; and no finding of that run that cites the fact is `conflicting` or `outdated`.

### Transactions

Approving with `resolve_impact_ids` writes the workflow event, overrides, the new status and every resolution in one transaction; if any resolution is refused, the approval is rolled back too. Revision creation writes the revision, correction records and the `created` event together.

### Development reset

`app.scripts.seed --reset` deletes a brand's history by temporarily disabling the append-only triggers inside its own transaction and re-enabling them before commit. It is a development tool; no API deletes history.

## Phase 5 Data Model: Guidelines, Policy Sandbox & Governance Intelligence

Phase 5 introduces persistent structures for brand guideline rules, historical rule versioning, inspectable lint results, and policy simulation replays.

```text
brands (id, name, ...)
  │
  ├─── 1:n ─── guideline_rules (id, brand_id, title, rule_text, category, severity, status, current_version, ...)
  │               │
  │               └─── 1:n ─── guideline_rule_versions (id, rule_id, version_number, rule_text, conditions, ...)
  │
  ├─── 1:n ─── guideline_lint_results (id, brand_id, rule_id, issue_category, explanation, suggested_action, ...)
  │
  └─── 1:n ─── policy_simulations (id, brand_id, rule_id, base_rule_version, proposed_rule_version, status, ...)
                  │
                  └─── 1:n ─── policy_simulation_results (id, simulation_id, content_submission_id, baseline_outcome, simulated_outcome, ...)
```

### Table Definitions

| Table | Meaning & Constraints |
|---|---|
| `guideline_rules` | The current record of a brand policy. Includes `title`, `rule_text`, `category` (`terminology`, `claim`, `tone`, `visual`, `compliance`, `general`), `severity` (`low`, `medium`, `high`), `status` (`proposed`, `active`, `retired`), `current_version`, `scope`, `conditions` (JSONB), `examples` (JSONB), and optional provenance (`source_document_id`, `source_page`, `source_excerpt`). Enforces composite FK `(source_document_id, brand_id)` preventing cross-brand references. |
| `guideline_rule_versions` | Immutable version history of every guideline rule. Each row records `(rule_id, version_number)` with `UniqueConstraint("rule_id", "version_number")`, the snapshot of `rule_text`, `conditions`, `examples`, `source_reference`, `change_reason`, and `created_by`. Updating an active rule appends a new version row without rewriting historical versions. |
| `guideline_lint_results` | Findings generated by the deterministic rule linting engine. Records `rule_id`, `rule_version`, `issue_category` (`vague_instruction`, `missing_conditions`, `missing_examples`, `missing_scope`, `potential_conflict`), `explanation`, `suggested_action`, and optional `related_rule_id`. Flagged items require human assessment and never mutate active rules. |
| `policy_simulations` | Isolated policy test run records. Stores `rule_id`, `base_rule_version`, `proposed_rule_version`, `proposed_rule_snapshot` (JSONB), execution `status`, `summary` counts (`total_evaluated`, `changed`, `unchanged`, `not_evaluable`), `created_by`, and timestamps. |
| `policy_simulation_results` | Outcome evaluation for one historical content submission under a simulation. Records `simulation_id`, `content_submission_id`, `historical_review_run_id`, `baseline_outcome`, `simulated_outcome`, `changed_findings` (JSONB diff), `explanation`, and `evaluation_status` (`evaluated` / `not_evaluable`). |

### Historical Protection Guarantees

1. **Content and Review Immutability**: `policy_simulations` and `policy_simulation_results` write strictly to their own tables. They **never update or delete** records in `content_submissions`, `review_runs`, `review_findings`, `finding_evidence`, `workflow_events`, or `fact_change_impacts`.
2. **Approval Gate**: Creating or simulating a proposed rule does not change `guideline_rules.status` from `proposed` to `active`. Only an explicit call to `PATCH /api/guidelines/{rule_id}` by an authorized reviewer activates a rule.
3. **Cross-Brand Isolation**: Foreign keys with composite brand constraints guarantee that guideline rules, source documents, content submissions, and simulations cannot span different brands.

## Phase 6 Data Model: Campaign Intelligence, Portfolio Audits & Release Readiness

Phase 6 introduces structures to group related content assets into campaigns, record immutable multi-asset audit snapshots, categorize audit findings with full evidence chains, and enforce guarded release decisions.

```text
brands (id, name, ...)
  │
  └─── 1:n ─── campaigns (id, brand_id, title, description, status, external_ref, ...)
                  │
                  ├─── 1:n ─── campaign_assets (id, campaign_id, asset_id, selected_submission_id, channel_role, ...)
                  │
                  ├─── 1:n ─── campaign_audits (id, campaign_id, audit_number, readiness_outcome, is_stale, ...)
                  │               │
                  │               └─── 1:n ─── campaign_audit_findings (id, audit_id, finding_category, severity, ...)
                  │
                  └─── 1:n ─── campaign_release_decisions (id, campaign_id, audit_id, decision, actor, ...)
```

### Table Definitions

| Table | Meaning & Constraints |
|---|---|
| `campaigns` | The container representing a coordinated marketing effort for a brand. Columns: `brand_id`, `title`, `description`, `external_ref`, `owner`, `status` (`draft`, `in_review`, `blocked`, `ready_for_release`, `released`, `archived`), `created_by`, `updated_by`, timestamps. Foreign key to `brands(id)` on delete CASCADE. Check constraint ensures `title` is non-empty. |
| `campaign_assets` | Membership record binding a content asset and its selected revision to a campaign. Columns: `campaign_id`, `asset_id` (the root submission/asset ID), `selected_submission_id` (the exact revision evaluated), `channel_role` (`landing_page`, `ad`, `email`, `social_post`, `product_spec`, `other`), `notes`, `added_by`, timestamps. `UniqueConstraint("campaign_id", "asset_id")` ensures an asset appears at most once in a campaign. Foreign keys to `campaigns(id)` and `content_submissions(id)`. |
| `campaign_audits` | Immutable snapshot of a multi-asset campaign assessment. Columns: `campaign_id`, `audit_number`, `readiness_outcome` (`blocked`, `needs_review`, `ready_for_release`), `is_stale` (boolean), `stale_reason`, `summary` (JSONB: blocker/review/warning/passed counts, checks run/skipped), `evaluated_asset_revisions` (JSONB snapshot of asset IDs, submission IDs, revision numbers, content hashes), `rule_version_snapshot` (JSONB), `fact_version_snapshot` (JSONB), `created_by`, `completed_at`. `UniqueConstraint("campaign_id", "audit_number")`. |
| `campaign_audit_findings` | Individual issue identified during a campaign audit. Columns: `audit_id`, `campaign_id`, `asset_id`, `submission_id`, `content_hash`, `claim_text`, `finding_category` (`cross_asset_contradiction`, `outdated_fact`, `open_impact`, `guideline_violation`, `missing_review`, `failed_review`, `human_review_required`, `workflow_unapproved`), `severity` (`blocker`, `warning`, `info`), `status` (`confirmed`, `potential`, `uncertain`, `unevaluable`), `explanation`, `suggested_action`, `requires_human_review` (bool), `fact_id`, `fact_version`, `rule_id`, `rule_version`, `review_finding_id`, `impact_id`, `source_document_id`, `source_page`, `source_excerpt`. |
| `campaign_release_decisions` | Append-only audit record of release status transitions. Columns: `campaign_id`, `audit_id`, `decision` (`ready_for_release`, `released`, `blocked`), `actor_name`, `actor_role`, `rationale`, `checklist_snapshot` (JSONB), `created_at`. Non-updatable audit trail. |

### Semantic Invariants & Integrity Guarantees

1. **Non-Destructive Association**: `campaign_assets` references `content_submissions` via foreign keys. Removing an asset from a campaign deletes only the membership row; it does not delete or alter the content submission, its revisions, its reviews, or its workflow events.
2. **Same-Brand Enforcement**: Backend service logic validates that any added asset belongs to the campaign's `brand_id`. Cross-brand asset additions are rejected with `422 Unprocessable Entity`.
3. **Revision Replacement & Invalidation**: Adding an asset with an updated `submission_id` replaces the selected revision, updates `updated_at`, and marks all existing audits for that campaign as `is_stale=True` with `stale_reason="Asset revision replaced in campaign"`.
4. **Staleness Tracking**: An audit is marked stale if asset revisions change or if fact/policy versions diverge after assessment. Stale audits cannot be used to release a campaign (`409 Conflict`).
5. **Guarded Release Transition**: A campaign may transition to `released` only when:
   - The latest audit has `readiness_outcome == 'ready_for_release'`.
   - The latest audit is not stale (`is_stale == False`).
   - Every individual asset in the campaign is in `approved` workflow status.
